# Build Guide: Xbox UWP

This guide builds the x64 UWP package for Xbox Dev Mode. The port keeps its
host, compatibility code, manifest, and assets under `ports/uwp`. The main
source tree still owns the game loop, SDL D3D11 renderer, input, audio, and
content handling.

Rendering, controller input, WASAPI playback, LocalState content loading, and
save-file creation were reported working on Xbox by the original PR author. This integration still
requires a local build and testing on hardware.

## Requirements

Install Visual Studio 2022 with the C++ UWP tools and Windows SDK
`10.0.19041.0`, plus LLVM/Clang, Ninja, CMake 3.24 or newer, and vcpkg.

Set the vcpkg checkout before building:

```powershell
$env:VCPKG_ROOT = '<path-to-vcpkg>'
```

Use vcpkg commit `80f9bcfa455e875d9c1bf7a7c6692d7e1e481061`. The same
revision is pinned in the workflow and `ports/uwp/vcpkg.json`. It builds FFmpeg,
mbedTLS, and zlib for `x64-uwp-static-md`. The patched SDL3-UWP 3.4.14 source is
committed under `ports/uwp/third_party/SDL3`.

## Build

Run the build script from the repository root:

```powershell
.\scripts\build\build-uwp.ps1
```

`Release` is the default. To include symbols, use:

```powershell
.\scripts\build\build-uwp.ps1 -Configuration RelWithDebInfo
```

CMake configures the matching preset and restores the vcpkg dependencies. The
generated package is placed under:

```text
ports/uwp/build/<preset>/AppPackages/SF3UWP
```

The script uses the pinned vcpkg revision declared in the manifest.
No build has been validated for this integration yet.

## Xbox One D3D11 shader compatibility

The UWP port uses Direct3D 11 at feature level `10_1`. Its advanced pixel
shader (including indexed texture palettes) is compiled as `ps_4_0` during
the build. FXC from the Windows SDK must be installed. CMake searches the SDK
binary directories and PATH; `SF3_UWP_FXC` can specify an absolute `fxc.exe`
path if automatic discovery fails.

The `SF3UWPShaders` target generates
`generated/shaders/d3d11/SF3_D3D11_PixelShader_Advanced_SM4.h` inside the preset's
build directory before compiling SDL3. Both the HLSL entry point and its shared
include are dependencies. SDL3 embeds this generated bytecode instead of its
precompiled `ps_5_0` header for this UWP build. Desktop builds keep their existing
shader selection. No global SDL installation is modified.

Run the normal UWP build script or reconfigure the existing CMake preset before
building in Visual Studio so the new shader target is available. The build must
stop if FXC is missing or shader compilation fails; there is no SM5 fallback in
this UWP configuration. Shader compilation and Xbox runtime validation remain
local validation steps.

After testing, copy `LocalState/data/uwp_render_check.log` before restarting the
app. For `shader=3`, the expected entry is `profile=ps_4_0 hr=0x00000000` with
`feature_level=0xA100`. The diagnostic also records the canvas dimensions and
viewport to check whether the menu scale recovers after successful shader setup.

## Xbox One performance diagnostics

Persistent diagnostic output is currently suspended. See `UWP Future Fix.md`
at the repository root for the investigation history and stopping point.
`include/port/uwp_diagnostics.h` sets `SF3_UWP_DIAGNOSTIC_DISK_LOGGING=0`:
no render/resource diagnostic files or desktop debug CSV/session files are
created by the UWP build. Existing console logs are not deleted. Measurement
hooks and the effect-table warm-up remain; the diagnostic writer is not started.
The version-specific logging instructions below are historical and require
explicitly restoring diagnostic output before use.

Version 17 experimentally reads the complete `_ef01_char_table` once per
process, on the first `Game2_1` update. The `[UWP_COMBAT]` record with
`kind=hit_effect_table_warmup` reports the read duration and checksum. This
does not spawn an effect or play audio; it tests whether touching these data
early changes the first-hit stall, and does not guarantee their residency.
An attract-mode fight can perform the warm-up before a player starts a match.

Version 18 adds `attack_entry_trace` for initial Ken and Hugo extra attacks at
state 16/0. Milestones are elapsed milliseconds from the dispatch start; -1
means a milestone was not reached. CPU time uses `GetThreadTimes` across the
call and may have coarse resolution; `cpu_valid=0` means it was unavailable.
The trace includes its own clock and bookkeeping overhead. The version 17
table warm-up remains enabled.

`uwp_render_check.log` version 18 uses the `UWP Diagnostic Writer` thread for
file writes and flushes. The main thread only queues bounded messages; it does
not wait for disk I/O or queue space. The queue holds 128 messages and occupies
516 KiB, including an extra ring slot to distinguish full from empty.
Version 5 uses atomic read/write indices and a semaphore wakeup instead of a
queue mutex. The vendored SDL serializes its log callbacks, providing a single
producer at a time; one worker consumes published messages. Only a full queue
drops messages, not mutex contention. This relies on the vendored SDL's serialization
and must be reviewed if its logging implementation is replaced.
Captured diagnostics are not also forwarded to the synchronous debugger output.
The worker flushes about once a second and drains the queue on orderly shutdown.
A forced termination can lose recent messages. The log is capped at 4 MiB.

`[UWP_LOG]` reports dropped messages, queue high-water mark, file-limit discards,
I/O errors and maximum worker flush time. Queue pressure drops diagnostic
messages only; it does not drop game frames, audio or resources.

`[UWP_PERF] window` summarizes 120 frames, including average/maximum times,
counts above 20/33.333 ms, texture creation counts/failures, and audio queue
snapshots. Up to eight slow-frame details per window identify the current
G/D state, frame phases, texture creation cost and screenshot cost. State changes
are also logged. These counters do not require the desktop debug CSV logger.
`legacy_debug_log=1` indicates that the separate desktop logger is also enabled;
its synchronous I/O can still affect performance.

`frame_ms` covers BeginFrame through EndFrame, including pacing. `work_ms`
excludes software pacing but includes any VSync wait inside Present;
`pre_render_ms` includes BeginFrame and game_step_0, including
texture creation there. Texture creation time is a subset, not an additional
phase to add to the total. `previous_begin_interval_ms` measures the preceding
BeginFrame-to-BeginFrame interval, including game_step_1, event polling and
diagnostic enqueue overhead. It belongs to the preceding interval, whereas the
other detail fields describe the current frame. Use `avg_begin_interval_ms` and
`max_begin_interval_ms` to assess full loop cadence. Phase timers measure CPU
elapsed time, including driver waits; they are not GPU execution timestamps.
Audio byte counts are snapshots and do not prove absence of underruns.
`[UWP_PERF] afs_sync` records up to 64 synchronous reads exceeding 2 ms, with
resource/thread IDs and completion status. A limit marker indicates when later
slow reads stop being detailed. Reads retain their existing behavior.

Verbose viewport/geometry and successful-texture messages are disabled by
default. Set the SDL hint/environment `SF3_UWP_VERBOSE_RENDER_TRACE=1` only
when investigating rendering correctness. Render/shader errors remain logged.
Shader Model 4, existing caches, audio loading and the simulation target are unchanged.
The session header reports main/logger thread IDs and logical CPU count; this
does not enumerate all process threads or establish an exclusive CPU allocation.

Version 4 enables indexed texture reuse by default on UWP, independently of the
desktop debug logger. It uses the existing indexed upload path: INDEX4 pixels
are expanded to INDEX8, with an RGBA streaming fallback if a palettized texture
cannot be created. Palette/pixel unlocks retain compatible cached textures that
have not been used in the current frame, then update them on demand. Textures
already referenced by this frame's render tasks retain their original data until
cleanup; a new cache entry is created if needed. Actual resource releases still
invalidate the cache. Dimension/format changes force recreation.

The SDL hint `SF3_UWP_TEXTURE_REUSE` is read at renderer initialization and defaults
to `1`; setting it to `0` before initialization provides the previous creation
path for comparison. `[UWP_RENDER] texture_reuse enabled=1 snapshot_protection=1`
confirms the selected path. Shader Model 4 and audio loading are unchanged.

`[UWP_PERF] cache kind=slow` accompanies detailed slow frames. `kind=window`
aggregates the same 120 frames as the preceding window record: counters/bytes
are summed, update times are per-frame maxima, and `largest_create` is the
largest created texture by area. `retained` counts entries preserved on unlock,
not a resident-texture count; `hits` counts existing cache entries encountered
before any update. Invalidation counts distinguish pixels, palettes and actual
releases. `snapshot_invalidations` counts entries invalidated to preserve queued
draws, while `resize_recreates` also includes incompatible format changes.
`upload_bytes` counts successful indexed/RGBA pixel uploads through the reuse
helpers, including initial uploads; it excludes palette data, driver staging,
alignment and default-path uploads. It does not measure GPU memory usage.
Pixel update timing includes conversion where needed and can overlap creation
timing for initial uploads. Stage/area IDs, player character IDs, background
world X and player X positions identify the context of slow records and state
transitions; window context is sampled at the end, not throughout the window.

Version 5 requests VSync interval 1 on UWP by default. The initialization-only
SDL hint `SF3_UWP_VSYNC=0` restores the previous unsynchronized mode for an A/B
test. `[UWP_RENDER] vsync` records the requested/effective SDL values, success,
display mode and reported refresh rate. Zero/unknown refresh information is not
proof of the physical TV mode. `[UWP_RENDER] d3d11_vsync` records actual backend
interval and flags; with interval 1 the expected present flags are zero.
`d3d11_present` reports cumulative calls, busy results (`DXGI_ERROR_WAS_STILL_DRAWING`),
other failures, last HRESULT and elapsed/max driver-call time. It logs the first
call, every 120 calls and the first eight busy results. Max time resets after
each such log. These calls include initialization and do not equal game-frame
IDs or prove that frames reached the display. Existing error handling is kept.

The original arcade/PS2 simulation target and absolute software pacing algorithm
remain in place. VSync can add blocking time inside Present, so assess its
interaction with the software deadline and the display's refresh rate on console.
In particular, 59.59949 FPS does not divide evenly into a fixed 60 Hz refresh;
occasional repeated display frames can remain even if tearing is eliminated.
This test does not change the simulation to 60 FPS or add frame skipping.

The existing game-step/task timers run on UWP even when the desktop CSV logger
is disabled. `[UWP_PERF] game`, `steps` and `tasks` report 120-frame per-field
maxima (`kind=window`) and up to eight detailed slow full-loop frames per window
(`kind=slow`, total above 20 ms). Game records include event polling, BeginFrame,
game_step_0, EndFrame excluding software sleep, and game_step_1. Step records
separate AFS completion handling, input, task execution, sprite draw preparation,
effects, flip and post-frame services. `game_main_ms` contains several other
steps and must not be added to them. Task records show the eleven task times,
the slowest task ID and its pre-execution state. For window records, each task
time is its own maximum and `peak_task_frame` identifies the largest task sample.
Window maxima can come from different frames and their scene context is sampled
at the end. These timers are elapsed CPU-side times, including any waits, not
proof of decompression, disk I/O or GPU saturation. CSV output remains disabled
unless separately enabled in configuration. Timers and logging add some overhead.

For the next console test, keep verbose rendering and desktop CSV diagnostics
disabled. Navigate title/menu, enter character select, play at least two rounds,
and repeat a mode transition. Compare the Alex stage with the quieter forest
stage, testing left, center and right positions and repeated attacks. Check
sprite animation, transparency, palette changes and super effects for visual
regressions. Check tearing during horizontal movement and whether control
response or overall speed changes with VSync. If possible, repeat Remy in the
same session and start a separate session with Alex to separate first-use work
from stage-specific cost. Note whether pauses occur only on first use or also on repetition.
Wait five seconds after the last action, then download
`uwp_render_check.log` and `uwp_resource_check.log` before restarting the app.
The last partial 120-frame window may not have a summary, but slow details and
state transitions are queued immediately. Build and runtime testing are local.

### Version 6: internal input timing

Gamepad button edges (including digital D-pad) are traced from the SDL event
timestamp through polling, a raw-state sample, the game's command-copy boundary
after appCopyKeyData, and the return of that iteration's RenderPresent. Axes,
keyboard, physical switch activation and TV scanout are not traced. SDL timestamps
may begin when the backend detects input, so this does not measure hardware input
latency. Present return is not a display timestamp or proof of a visible response.

`[UWP_PERF] input` includes device/slot/button/direction, timestamps, elapsed times,
raw-state agreement, eligibility and the two PLsw command masks at the copy
boundary. This is a temporal correlation, not proof that this individual button
was mapped to a command, accepted by gameplay, or produced an animation. A button
press and release pumped together can legitimately disagree with the final sampled
state. Focus suppression, screenshot chords, unmapped devices and absent samples
must not automatically be interpreted as lost inputs. No input behavior changes.

`event_to_present_return_ms` includes VSync and game work after polling, and can
reveal a delayed presentation opportunity during a game stall. `present_ok` is
SDL's return status; correlate with DXGI busy/failure counters. Missing stages or
invalid/zero/future event timestamps have elapsed values of -1. The bounded
128-event scratch buffer drops trace records only when full. `input_window`
summarizes all collected events every 120 frames, including overflow, uncorrelated
events, invalid timestamps, detail omissions and maximum internal elapsed times.
Detail output is capped per 120 frames at eight normal events plus sixteen events
with event-to-present-return time above 40 ms. Counts continue after that cap.

To reduce file size, routine cache and game/step/task window records are emitted
every 600 frames, describing only the most recent 120-frame window; intermediate
windows are not retained. Frame cadence and input summaries remain every 120
frames, and existing slow-frame details remain enabled. The 4 MiB file limit and
logger loss counters still apply. Keep logs short for this input-focused test.

Test repeated single button presses/releases, held directions, quick taps and
normal combos during combat. Include menus and a naturally occurring hitch;
avoid intentionally changing gameplay timing. Note any perceived delayed command.
Wait five seconds, then copy both diagnostic logs before restarting the app.
Expect render_trace_version=6. External high-speed measurement is still required
for physical-button-to-visible-response latency. No build or hardware validation
was performed by the agent.

### Version 7: TASK_GAME subphases

This test preserves VSync, input processing, texture reuse and simulation order.
It times the existing Game_Task calls without moving work to another thread.
`[UWP_PERF] game_phase` details operations taking at least 1 ms on the same
slow frames selected by the existing game profiler (up to eight per 120 frames).
Durations/call counts aggregate within one frame, including repeated sysFF
iterations. `dispatch` is inclusive: it contains gameplay subphases and must not
be added to their times. Cache preparation, sprite cache update, load request
processing, rumble, screen/background checks and sound-code display are separate
task phases. During Game2_1, players, stage update, management, background/player
drawing, basic effects, VRAM purges and hit checking are also measured. Other
gameplay states remain represented by dispatch. HUD and other uninstrumented
work may account for a difference between dispatch and its listed subphases.
These are elapsed times and include waits; they do not identify CPU usage alone.

`d3d11_present` now includes cumulative `slow_over_40ms`. The first sixteen calls
above 40 ms receive immediate records, in addition to the existing periodic and
busy-result records. This helps correlate exceptional driver waits with nearby
game/input frames; driver call IDs still differ from game frame IDs.
Input tracing and its rate limits remain unchanged. Expect render_trace_version=7.
For this test, play from character selection through at least two full fights,
noting first-round pauses and any later hitch. Wait five seconds and collect both
logs before restarting. Build and runtime verification remain local.

### Version 8: console fullscreen presentation

**Console result: this attempt did not remove the outer margins.** Its 4:3
rectangle policy remains in version 9, but fullscreen flags and the rectangle
alone did not establish the physical presentation size. The available Downloads
render log has `render_trace_version=7`, build `Oct 29 2026 18:29:06`; it cannot
be used as runtime evidence for version 8 or version 9.

UWP ignores saved desktop window dimensions when a valid desktop display mode is
available and requests fullscreen at that reported size. It does not force a
1920x1080 resolution. Fullscreen is requested again on focus gain; keyboard
fullscreen toggles are disabled on UWP. Pixel-size events refresh the screen
target. The UWP path uses nearest filtering, a full-height 4:3 fit on widescreen
outputs and no bezels, ignoring saved stretch/integer/soft-linear options without
overwriting the configuration file. Desktop options remain unchanged.

The game area is 960x720 at a 1280x720 output or 1440x1080 at 1920x1080, with only
side bars. `[UWP_RENDER] presentation policy=fullscreen_4_3` records actual window
pixel dimensions, canvas and destination rectangle on size changes. Verify the
whole console view is occupied and no top/bottom margins remain. A reported
fullscreen flag alone does not prove the physical output geometry; compare the
image with these dimensions. Expect render_trace_version=8. VSync and the existing
phase/input diagnostics are retained. Runtime validation remains on console.

### Version 9: physical-pixel swap chain and full Xbox view

Static inspection found that the WinRT D3D11 backend sized its swap chain with
`SDL_GetWindowSize` (logical units), while SDL's renderer and screen texture use
`SDL_GetWindowSizeInPixels`. The CoreWindow swap chain also selected
`DXGI_SCALING_NONE`, leaving a smaller buffer unscaled in a larger presentation
target. This is a concrete mismatch in the presentation chain; the precise
origin of the centered outer margins still requires the new console logs.

The backend now creates/resizes buffers in physical pixels and selects
`DXGI_SCALING_STRETCH` for WinRT CoreWindow presentation. This fits the composed
surface to the view; the game remains inside its full-height 4:3 rectangle, with
side bars included in that surface. The desktop HWND path is unchanged. The Xbox
view requests `UseCoreWindow` bounds and native fullscreen before renderer
creation. HDMI/output geometry is refreshed on resize, orientation, DPI changes
and activation. The Xbox override no longer writes SDL's `last_pixel_w/h` before
event delivery, which could suppress `PIXEL_SIZE_CHANGED` and leave old buffers
in use. Gaming-device queries now check their HRESULT with `SUCCEEDED`/`FAILED`.

No shaders, feature levels, VSync settings, input timing or texture-cache policy
are changed. Saved presentation options in `LocalState/data/config` are logged
as `saved_presentation` and overridden in memory by the existing UWP policy;
the file is not rewritten by this presentation change. No settings reset is
required. Native-view and final-viewport diagnostics are enabled without verbose
per-frame logging.

After a local build and install, verify menus and gameplay, then leave/re-enter
the app once to exercise activation. Wait five seconds before collecting
`uwp_render_check.log` and `uwp_resource_check.log` from the same session. Check:

- The render header says `render_trace_version=9` and identifies the new build.
- `winrt_view_policy` reports the bounds/fullscreen request results. `winrt_view`
  records CoreWindow/VisibleBounds in DIPs, DPI, raw scale, raw screen pixels,
  resolved output pixels, native fullscreen and the bounds mode. Logical
  `1280x720` can be valid for a physical `1920x1080` view at 150% scale.
- For a resolved 1080p output, `d3d11_backbuffer` should report
  `requested=1920x1080 actual=1920x1080`, `window_pixels=1920x1080` and
  `scaling=0` (`DXGI_SCALING_STRETCH`). A mode with `refresh_hz=0` still means
  unknown refresh rate; this patch does not infer 60 Hz from it.
- `presentation` should report `output=1920x1080 canvas=1920x1080` and
  `rect=240.0,0.0,1440.0,1080.0`. `stage=window_presentation` records the final
  viewport, scale, clip and logical-presentation state on the first frame and
  size changes. Normally these are viewport `0,0,1920,1080`, scale `1,1`, clip
  disabled and logical mode `0` (disabled).
- Confirm on the TV/capture that content reaches the top and bottom, with only
  side bars. If the resolved output is 720p, inspect native/raw geometry and the
  output-resolution source before treating it as 1080p evidence. The swap-chain
  scaling policy should still cover the full view; a log of buffer dimensions
  alone cannot establish physical TV geometry.

Only static verification was performed by the agent. No build, shader
compilation or console validation was run; the visual result is pending the
user's Xbox test.

### Version 10: first-impact diagnostics, without input tracing

The UWP event/sample/command-copy correlation and `input`/`input_window` records
are removed. Controller polling, command copying, screenshot chords and their
order are unchanged. Existing coarse game-step timings, including pad/input
time, remain available. Version 9 presentation, VSync, shaders and texture reuse
are unchanged; this version diagnoses the stall rather than applying a fix.

`[UWP_COMBAT]` samples are collected only in the gameplay state (`G=2,2,...`),
then emitted after EndFrame so their `frame` matches the existing performance
records. Each sample includes a monotonic `at_ns`, `kind`, `subject`, `detail`,
`value`, `elapsed_ms` and `event`. Event records (`event=1`) mark occurrences;
their zero duration does not mean the operation took zero time. Timed records
are retained only at or above 1 ms and are inclusive, including possible waits.
Nested measurements must not be added together.

| Kind | Subject | Detail | Value |
| --- | --- | --- | --- |
| `player_total` | player slot | routine on entry | internal character ID |
| `player_commands` | player slot | routine on entry | internal character ID |
| `player_routine` | player slot | routine immediately before dispatch | internal character ID |
| `vital_change` | player slot | vitality before Player_move | vitality after |
| `combo_change` | player slot | combo count before Player_move | combo count after |
| `hit_combo` | attacker slot | defender slot | attack kind |
| `first_attack` | combo-control player index | internal character ID | first_attack state |
| `first_attack_notice` | combo-control player index | notice kind (4) | 0 |
| `effect_callback` | effect ID | effect group | effect routine on entry |
| `impact_spawn` / `impact_init` | source work ID | hit-mark index | mark type (`mkst`) |
| `impact_sound` | effect master ID | requested sound ID | 0 |
| `players_setup` / `players_dispatch` | -1 (both players) | controller state `[0]` | controller state `[1]` |
| `players_collision_state` | -1 | 0 | 0 |
| `player_hit_push` | player slot | 0 | 0 |
| `players_position` / `players_afterimage` | -1 | 0 | 0 |

Player slots are zero-based; internal character IDs are not select-screen
numbers. Player routine bytes `[0..3]` are packed from most to least significant
byte and also printed as `detail_hex`. `player_commands` measures waza_check or
key_thru; `player_routine` measures the dispatched player routine, including
attack/reaction work. `impact_spawn` means effect 02 was allocated successfully;
it does not itself prove unguarded damage. `hit_combo` marks add_combo_work, while
the first-attack notice has its own marker. `combo_hud` is also measured as a
game phase. Events can precede a slow reaction by a frame, so inspect nearby
frames rather than requiring all markers on the same frame.

Storage is fixed: 64 details per frame, up to 512 events and 1024 timed records
per application session, independent of the older slow-frame detail quota.
`[UWP_COMBAT] limits` reports omitted samples every 120 frames when necessary.
Samples use the existing bounded asynchronous logger; no synchronous file writes
or dynamic allocations were added to these combat hooks. Timing and logging do
add overhead, so treat this as a diagnostic build.

For the local Xbox test, confirm `render_trace_version=10`. Start versus with the
same characters/stage, land one isolated opening hit, pause briefly, and repeat
the same hit several times. Return to character select and repeat the matchup
without closing the app. Avoid additional matches before collecting both logs
so the event budget remains focused on first-use behavior. Wait five seconds
before collection. Correlate the first `hit_combo`, `impact_spawn`, vitality and
`first_attack` markers with `player_routine`, effect and sound timings, including
the following few frames. Compare the opening hit in both matchups. No verbose
render logging is required. Build and Xbox validation are performed by the user;
the agent performed static checks only and did not compile shaders or run a build.

### Version 11: narrow down Hugo's pre-impact routine

The version 10 test located a 101 ms call in Hugo's routine `04,00,04,01`,
19 frames before the first hit. This dispatches Player_normal / Normal_04000,
which updates motion and animation, rather than the Player_attack branch.
Version 11 retains the impact markers and removed input tracing, and adds:

| Kind | Subject | Detail | Value |
| --- | --- | --- | --- |
| `active_state` | player slot | routine `[1]` before dispatch | internal character ID |
| `active_gauges` | player slot | routine `[1]` | internal character ID |
| `normal_state` | player slot | routine `[2] << 8` plus `[3]`, before dispatch | internal character ID |
| `normal04_speed` / `normal04_position` / `normal04_animation` | player slot | animation char_index on entry | internal character ID |
| `animation_opcode` / `animation_opcode_alt` | source work ID | animation command opcode | work_id |
| `animation_pattern` | source work ID | cg_ix on entry | work_id |
| `animation_effect_init` | source work ID | effect ID before init | work_id |
| `animation_sound` | source work ID | cg_se before sound request/filter | work_id |

Animation command timings cover both decoding paths. Each decoder executes once
with its original return-value branch. Pattern timing includes its nested effect,
sound and hit-area setup calls; durations remain inclusive and must not be added
together. Timing records below 1 ms are still omitted, and version 10's budgets
and asynchronous output remain in effect. No routine order, input, shaders,
VSync, resolution or gameplay rules have been changed.

Use the same two-match test as before: launch the app, select the same matchup
and stage, land one isolated hit, return to character selection, and repeat once
without closing the app. Preserve the same approach/movement before the hit.
Wait five seconds and collect both logs before restarting. Confirm
`render_trace_version=11`. Compare the pre-impact slow routine with the new
nested timings and the corresponding repeated movement. No build or shader
compilation was performed by the agent; Xbox validation remains local.

### Version 12: unique gamepad sources and resident-sound diagnostics

UWP selects WGI and explicitly disables XInput before initializing gamepads,
using override-priority hints. The older identical-instance-ID check remains;
after opening a pad, assignment also rejects an already assigned handle or
instance ID. Two controllers of the same model remain valid: names, VID/PID or
GUIDs are not used as unique physical identities. This addresses possible
cross-provider duplication, but requires validation with the wired controller
and wireless controller on the Xbox One S. Desktop provider selection is unchanged.

`[UWP_PAD] providers` reports hint selection results; `assigned` reports the
zero-based slot, SDL instance ID, name and path. `duplicate_event`, `duplicate_open`
and `removed` describe lifecycle events only. Per-button input tracing remains
disabled. Confirm that two distinct instance IDs occupy slots 0 and 1, and that
each physical controller moves only its corresponding selection cursor. Then
test reconnecting each controller separately without filling both slots with
one device. Slot order follows connection/enumeration order, not a saved physical
controller identity; both controllers must remain independently usable.

Sound effects already have resident sample storage: loaded banks are copied by
SPU_Upload into 2 MiB of emulated SPU RAM; starting a voice uses an address in
that RAM. The normal CSE/TSB voice-start path does not open an individual audio
file per hit. ADX music has a separate loader/buffer pool. Therefore this version
does not add a second effects-file cache or claim that disk I/O caused the stall.
Runtime ADPCM decoding and synchronization can still cost time. In particular,
the SPU audio callback holds soundLock while generating requested samples and
submitting stream data; main-thread sound operations share that mutex.

`[UWP_AUDIO]` records calls taking at least 1 ms, with separate per-session
limits of 128 records per category, emitted after releasing soundLock:

- `voice_start`: bank/note, result (1 started, 0 filtered, -1 no free voice),
  `lock_wait_ms`, `locked_work_ms` (including unlock overhead), and `total_ms`.
- `spu_upload`: destination/byte count and the same wait/work/total split.
- `tsb_request`: bank/code, result, and inclusive request time. This wraps the
  TSB request, not an additional disk read; nested voice times are not additive.

The voice and upload diagnostics do not change locking, decoding, bank loading
or playback order. No logging was added directly to the audio callback. If a
long request is mainly lock wait, another file cache would not address that wait;
if new bank uploads coincide with first use, investigate their loading source
and consider preloading only the required banks before gameplay. First confirm
`render_trace_version=12`, independent controllers, and then repeat the same
two-match, one-hit test. Wait five seconds before collecting both logs. The agent
performed static verification only, with no build or shader compilation.

### Version 13: collision preparation, comparisons and debug drawing

`[UWP_COLLISION]` contains main-thread totals reset at SDLApp_BeginFrame and

| Fields | Meaning |
| --- | --- |
| `updates`, `update_ms` | set_jugde_area calls/time for player slots 0, 1, and all other work objects |

| `queued` | accepted queue insertions across all passes in the frame |
| `duplicates` | accepted insertions whose WORK pointer was already in the current queue |
| `rejected` | insertions rejected because the queue is full or cg_hit_ix is zero |
| `queue_peak` | maximum queue occupancy before it is cleared; not the frame insertion total |
| `attack_pairs`, `catch_pairs` | candidate-pair loop visits after initial self/result filters; not unique pairs or successful overlaps |

## Packaging and signing

This branch does not change the desktop release workflow. The local build produces
an unsigned package. Sign it with a code-signing certificate whose subject is
`CN=3SXW` before deployment when required by the console. Keep private keys and
passwords outside the repository. Install the matching x64 VCLibs framework dependency.

## Game data and storage

Do not package `SF33RD.AFS`, disc images, ROMs, or saves. Transfer a legally
obtained `SF33RD.AFS` through Xbox Device Portal to:

```text
LocalState/resources/SF33RD.AFS
```

Configuration, saves, and logs are written under `LocalState/data`. Press View
and Menu together to save screenshots under `LocalState/prints`.
On first launch, the bundled bezels are copied to `LocalState/data/img`. Existing
files in that folder are left unchanged.
Runtime code remains in the installed package.

## Xbox deployment

Install the signed MSIX and its framework dependencies through Xbox Device
Portal. Import the included public certificate if the console does not already
trust it.

## GitHub Actions: UWP branch

Push commits to `UWP` to run only `Build (Xbox UWP)`. Desktop push workflows
remain restricted to `main`; their jobs also skip PRs originating from `UWP`.
Do not create release tags for experimental builds: release tags still trigger
the existing multi-platform release workflow.

The Windows runner builds only `SF3UWP`, restores cached vcpkg dependencies,
and cancels older runs on the same branch. The first dependency build can take
substantially longer than later cached runs.

Download `3SXW-Xbox-UWP-test` from the completed Actions run. Extract the artifact
ZIP and then its inner ZIP. The package includes the signed MSIX, x64 VCLibs,
public test certificate and installation instructions. Private keys are not uploaded.
Each run uses a new temporary test certificate and version 1.0.0.0; this is for
fresh test installations, not a stable update channel. Back up LocalState before
uninstalling an earlier test package. A persistent certificate and incrementing
versions will be needed for dependable updates preserving installed app data.

If compilation fails, inspect the failed step and `Xbox-UWP-diagnostics` artifact.
No local build is required for this workflow.
